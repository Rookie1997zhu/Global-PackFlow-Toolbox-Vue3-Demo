源码发现：需立即排查的既有问题
  • 缺失数据被自动填成样例： mappedToCargo.ts 和 mappedToPalletCartons.ts 对尺寸 / 重量采用示例默认值；正式服务端应返回字段错误，不能伪造 40×30×20 cm 或 5 kg。
  • 发布脚本不一致： deploy-pages.yml 使用 npx vite build，而 package.json 的 npm run build 才包含预渲染。应统一 CI 构建命令。
  • 数据币种不完整：当前 Cargo.price 是 number，scheme v1 无明确币种字段，需 v2 引入 currency 和数值精度策略；不能推断全部业务价格为 USD。
  • 文件路径风险： pdf.ts 写死 /fonts/NotoSansKR-Regular.otf；部署到子目录时需回归校验。
  • 校验需强化：现有部分前端清洗函数将非法数字转 0，导入面板还能继续提交带问题的行；服务端必须严格拒绝未满足业务规则的数据。

说明：这些是静态源码中可见的实现和风险；本次并未在本地克隆和运行完整仓库（当前执行环境无法解析 github.com），因此测试通过率和生产环境表现均不做臆断。

PostgreSQL所有权、对象元数据、方案修订版、任务和配额。第一阶段必须。
Redis + Celery文件解析、报告、较慢计算、重试、周期清理。第一阶段按实际任务量启用；不应让请求超时。

关键原则：公共网页与私有 API 分离
SEO 独立页面照常预渲染、可以匿名访问。/api/v1/* 仅为业务数据服务；不强迫用户登录才能打开工具。建议同一主域名通过反向代理访问 API，从而减少跨域和 Cookie 问题。

数据主权与规范化规则
外部 scheme v1 保持 cargo[] 中的 length/width/height=cm、weight=kg。内部计算装柜/卡板统一转换为 mm/kg；金额数据库存 Decimal/NUMERIC，API 传价格字符串和 ISO 币种（KRW/USD/CNY 等）。通过明确的 adapter 映射，禁止到处散落单位换算。

版本方案：SchemeRevision 使用追加式版本，前端 updatedAt 由服务端维护，row_version 用于乐观锁。修改前必须提交期望版本；不匹配返回 409 并提供冲突合并选项。meta 保持兼容，但需要白名单、层数和体积限制。

约定项正式协议建议
API 路径统一 /api/v1/；认证用户所属 team 从服务端 session/membership 推导，团队切换必须校验权限。
日期/时间RFC 3339 UTC（如 2026-11-09T09:00:00Z）；展示转换 Asia/Seoul；updatedAt 只由服务器签发。
计算单位货物 v1 维度 cm / 重量 kg；引擎侧 mm / kg；每个请求及结果写明单位。
金额以后新增显式 currency 与十进制字符串；不得用 double 处理付款金额。
幂等POST /jobs、文件提交、支付、方案导入使用 Idempotency-Key。
并发PUT/PATCH 传 If-Match 或 rowVersion；冲突返回 HTTP 409。
分页?page=1&pageSize=20，限制最大 pageSize；按团队过滤。
错误固定机器码和 requestId；KO/ZH/EN 翻译由前端负责，服务端不发送不可解析的自然语言错误作为唯一依据。
成功响应初期采用 API 草案的 {"ok":true,"data":{...}}，必要时增加 requestId；后续版本化，不混用不同返回结构。

CHAPTER 09

计算引擎：TypeScript 复用与服务端可信计算

关键决策：Python 管业务事务，TypeScript 保留已验证的领域算法。

路径优点风险 / 推荐时机
A · 仅浏览器运行算法最快；完全保留当前 V1.2 Worker 体验。结果可被前端篡改，不可作为可信计费/团队审计依据。仅适合匿名预览和非权威缓存。
B · TS 独立 Engine Service（推荐）复用现有 packing、pallet、nesting、CAD 的计算逻辑；Django 只调用内部 API。需要隔离资源、实现纯函数入口、错误契约和版本化；专业计算上线时启用。
C · 改写 Python 算法同一语言部署，适合 Python 优化库/特殊研究。重复开发成本高、算法可能漂移；除非测试表明性能/专业算法需要，暂不做。

推荐计算流程

  1. 用户在 Vue 编辑数据，已有 Worker 即时给出 预览结果，标注“未由服务端验证”。
  2. 提交云端计算时，DRF 验证成员权限、权益额度、输入、方案 revision 和文件可用状态。
  3. 数据库事务创建 CalculationJob（queued）和输入快照；提交成功后触发 Celery。
  4. Celery Worker 读取不可变输入，按 engine registry 调用内部 Node TS service；超时、并发、内存和实例上限按套餐控制。
  5. TS 引擎返回 placements / unplaced / warnings / strategy 等现有 DTO；服务端二次执行边界、碰撞、尺寸、资源约束检查。
  6. 结果和元数据存 PostgreSQL / 对象存储，标记 serverVerified、engineVersion、inputHash。
  7. 前端轮询 Job，成功后下载报告；失败显示可定位的错误码、重试条件和不会多扣额度的说明。

引擎输入的量纲契约

引擎沿用的源码输入服务端统一标准安全边界
CBM / 运费Cargo length/width/height cm、kg；ChargeMode按输入单位规范化；汇率锁定快照、精度与计费口径价格比较需要 FX；结果非承运商正式报价。
ContainerLoadSku + ContainerConfig；坐标 / 尺寸为 mm固定 mm/kg，保留旋转/stackable当前 400 实例上限；支撑/碰撞不等同重心、绑扎和车辆安全。

Sheet Nestingmm 的 sheetWidth/height、margin、kerf、parts固定 mm，记录 MaxRects / Guillotine当前 5000 实例上限；生产切割要求工艺复核。
Dieline CADTemplate ID、参数、刀版 geometry版本化 template/params，保留 2D/3D 与 SVG/DXF从现有 JS 抽取纯计算层；出口版权/工艺能力单独审核。

任务状态机与幂等

JOB STATE MACHINE
queued -> running -> succeeded
   |         |   |         | -> failed (retryable / terminal)
   |         -> cancel_requested -> canceled
   -> canceled / expired

唯一键：team_id + idempotency_key + normalized_input_hash
记录：attempt, engine_version, timeout, resource_cost, error_code
规则：相同幂等键重试不生成重复扣额；已结束任务不得无条件重跑。

Celery 实施细节：使用事务提交后入队（transaction.on_commit）；任务按 jobId 读取数据库而不是把敏感完整输入直接塞进 Redis 消息。长任务按队列分组并限制并发，worker 的取消必须是协作式或进程级可中断；客户端取消不代表数据库中已回滚。

CHAPTER 15

安全、隐私与业务数据边界

多租户和文件处理比登录页外观重要得多。

威胁 / 风险控制要求必须测试
越权 / IDOR所有资源查询以 team 范围过滤；读、改、删、列表、文件下载、任务状态全覆盖。A 团队尝试访问 B 团队 scheme、report、job 返回 403/404。
CSRF / 会话劫持CSRF token、HttpOnly + Secure Cookie、HSTS、会话撤销。跨站表单无法触发修改；登出后会话无效。
恶意上传允许格式、类型检查、大小限制、ZIP bomb 检测、文件名清洗、扫描隔离。伪装的 XLSX、超大表、畸形文件被拒绝。
CSV / Excel 注入导出写入时对前导 = + - @ 等危险公式开头进行安全处理；Excel 公式不得执行。文件在 Excel 打开后不能触发任意公式链接。
任务资源耗尽CPU/内存/时限/文件大小/单位数量按团队配额；队列隔离、限速。恶意极端输入不会拖垮 API。
计费篡改服务端价格、套餐校验；支付 webhook 验签+幂等+金额校验。前端改 amount/planId 不可白嫖。
隐私泄露最小化日志、脱敏、数据删除工作流、短时文件访问权限。日志和报错不包含原始客户表格或 access token。
供应链依赖扫描、锁文件、第三方字体/素材/模板许可确认。许可证清单与漏洞审计有记录。
额外注意：已有公开仓库素材
刀版模板、字体文件和材质资源已在当前公开仓库中出现。商业化 SaaS 前应逐一确认可再分发、可商用及商标/设计来源，不应仅因为文件可下载就推定已取得商业许可。
CHAPTER 16

Demo → SaaS 数据迁移与兼容

支持用户把已有浏览器方案带到云端，而不是要求从头录入。

版本桥接策略

  1. 定义 Python SchemeV1Serializer，以仓库 scheme.ts 为依据建立 golden fixture。禁止客户端 updatedAt 覆盖服务端时间。
  2. 提供 /schemes/import-demo/：读取现有 JSON，预览数量、币种缺失、无效尺寸、重复 ID、冲突名称。
  3. 为导入文件生成 sourceHash，服务端写入 owner/team 并分配稳定 UUID；保留 legacyId 用于重放去重。
  4. 方案数据写入 scheme_revisions revision 1；生成旧 ID → 新 ID 对照，必要时前端存映射。
  5. 当需要 KRW、多个价格精度、客户字段时推出 scheme v2；提供 v1→v2 migration reader，版本号不可默默覆盖。
  6. 同步时采用 rowVersion/If-Match：本地修改与云端修改冲突时展示对比并让用户选择“保留两个版本 / 使用云端 / 使用本地”。
  7. 保留旧版本导入器一段兼容窗口；移除前应调查仍在使用旧 JSON 的用户比例。

CHAPTER 19

关键架构决策与反模式

提前记录取舍，减少后期推翻重写。

决策点推荐选择不建议现在做什么
后端框架Django 5.2 LTS + DRF（以锁定兼容依赖为准）；Python 3.12/3.13 合适版本。为追求“最新”盲目升级大量插件。
数据库PostgreSQL，一开始就建立 team_id 与 revision 策略。把一切塞进一张 JSON 表，后期难审计。
业务组织Django 模块化单体；内部 adapter 层。13 个工具各拆一套后端微服务。
算法策略保留 TypeScript 确定性计算核心，云端需要时以 TS engine sidecar 执行。直接双份 Python/TS 逻辑长期并行但无一致性测试。
异步队列Celery + Redis broker；DB 持久化任务状态。用 Redis 任务消息当唯一持久状态。
身份同站 HTTPOnly Session + CSRF 为浏览器首选，API Token 留给未来外部集成。把长效 access token 放 localStorage。
存储私有对象存储、固定生命周期、授权下载。把 XLSX/PDF 存在公开 GitHub Pages 或直接暴露 OSS key。
计费设计 UsageLedger/Entitlement，不急着收款。根据前端 plan 标签直接扣费或授权。
国际化语言、币种、单位、时区分离；KO-first 但不锁死韩国。把韩文文案硬编码在服务端业务逻辑。
合规按实际数据流评估 PIPA 和商业授权。未经确认就说所有韩国用户必须存韩国本地，或忽略跨境个人信息。
