CHAPTER 04 · DATA

统一业务数据模型：先定义“件、箱、卡板、集装箱”

这是整个改造的逻辑核心。旧 Cargo v1 不删除，但正式出货业务不能再复用一个含义不明的 qty 字段。

业务对象英文 / 韩文必要数据不能混淆
商品行 ProductLine제품 / 품목SKU、description、productQty、unit(PCS/SET)、单价及币种productQty 是商品销售/发票数量，不是纸箱数量。
包装规格 PackagingSpec포장 사양每箱产品数、外箱 L/W/H、材质、外箱皮重、是否可叠放每箱件数 ≠ cartonCount；内尺寸/外尺寸不同。
实际包装行 CartonBatch박스 / 카톤cartonCount、cartonNoRange、unitsPerCarton、lastCartonQty、单箱 GW/NW不能把总商品件数假定为总箱数。
卡板装载 PalletPlan팔레트 적재palletPreset、carton placements、层数、卡板重量、装载约束不应把卡板自重忽略在承载、装柜总重之外。
集装箱方案 ContainerPlan컨테이너 적재containerSpec、cartons/pallets、placements、unplaced、weight装入对象必须注明 cartons / pallets；不可混成 product SKU。
出货作业 Shipment출하 작업teamId、shipmentNo、customer、PO、status、revision、关联方案与单据Shipment 不是完整 ERP Order；用于组织一次实际出货的所有资料。
正式单据 DocumentSnapshot출하 서류documentKind、sourceRevision、lineItems、totals、currency、作者/时间必须与用户确认后保存的实际明细保持一致。
旧 v1 兼容决策
cargo[].qty 只能作为既有工具的“处理单元数量”保留，不能在迁移时自动解释成 PCS 或 CTN。对缺少数量含义的历史方案标记 quantityBasis=unknown，要求用户明确确认后才生成正式 PL/CI。旧 Demo 可浏览和匿名预览，但不能默认为可信商业资料。

由数量推导箱数时的明确规则

  • 当 productQty=120、unitsPerCarton=12 时，cartonCount=10；每箱数量明确为 12，合计严格等于 120。
  • 若 121 PCS / 12 PCS 每箱，需 11 箱，其中第 11 箱为 1 PCS；生成数据必须记录 lastCartonQty=1，不能把 132 PCS 写进 Packing List。
  • 当同一 SKU 分多种箱规或存在混箱，允许多行 CartonBatch，按每行实际件数累计；需要时支持一个箱内多个 SKU 的 CartonContentLine。
  • 毛重、净重使用明确测量口径：per_carton 或 total；不能单凭 0.92 固定比例得出“实际净重”。
  • 金额使用 decimal 字符串（如 "12.50"）以及 KRW/USD/CNY 等明确币种；不同币种不可直接相加。
  • Container/Pallet 优化时输入的是实际外包装处理单元；运算维度内部用 mm，价格仍不参与几何计算。
CHAPTER 05 · P0

P0 修复：单据、共享数据、服务端计算必须一致

先处理可直接影响客户出货数据和计算可信度的问题。建议单独出 V1.3.1 补丁版本，不夹带新大型功能。

P0-A. Packing List 数量与重量

当前代码问题目标行为
packing_from_cargoqty 当箱数、qtyPerCarton 固定 1、netKg=grossKg×0.92货物数量基准明确；实际箱数/每箱件数/箱号/单箱重量由确认数据得出；不静默造值。
packingFromCargo前端也包含 0.92 净重假设、qty 即箱数统一数据契约；旧计算仅可作为“未确认草稿”，界面明确警告并阻止正式导出。
PDF renderer可生成格式合法但数据未确认的“正式” PDF导出前验证业务字段，PDF 增加来源修订、生成时间、草稿/正式状态。

P0-B. 云端报告不得忽略 UI 已编辑的行

  • 现有 PL/CI 组件都有可编辑的 lines；cloudExport() 调用 ensureSchemeId(cargo)，服务端从 cargo 重新生成，导致前端编辑的 qtyPerCarton / netKg / carton ranges / invoice description / unitPrice / unit 等不能保证进入云端报告。
  • 增量拓展 POST /api/v1/reports/：增加 sourceMode: "confirmed_lines" 和严格校验后的 lines；服务端生成不可变 DocumentSnapshot，再据同一 snapshot 生成 PDF/XLSX。
  • 旧 scheme_only 模式保留短期兼容，但只能按真实字段构建：缺少 cartonCount/净重时返回明确错误或输出显著的 DRAFT/미확인 标签。
  • 前后端预览与导出共用规范化的业务结果：前端对比 snapshotHash 或完整 line summary；不允许在下载时再悄悄运行另一套默认规则。

P0-C. 云端装柜不能篡改共享价格和 SKU 约束

  • 修改 ContainerLoading.vue::cloudVerify：不要调用 setCargo 覆盖全局 price，只构造只读提交快照。
  • 新增 loadSkuOptions[] / job params.skus[]，按 SKU stableId 传递 allowRotate、stackable，必要时增加 maxTopLoadKg / uprightOnly。
  • backend/apps/calculations/adapters.py 不再把 stackable 默认全部设置为 true；显式承认 unknown 并要求用户确认。
  • 引擎与浏览器必须使用相同的输入规范化、同一个固定 fixture，确保计算结果在允许的确定性误差内一致。
  • 改名或解释 serverVerified：只能代表已由服务器运行已版本化算法并完成几何规则验证，不代表运输安全认证。

CHAPTER 12 · V1.6

新功能五：仓库扫码核对（V1.6）

利用现有 Shipping Label 的 Code128/QR 能力与 Document Checker 逻辑，建设出货现场可用的防漏箱工具。

操作步骤

步骤后台行为用户体验
01 生成装箱明细对已确认 ShipmentRevision 生成 carton-level manifest 和唯一 cartonCode。显示 cartonCount、扫描任务、待发箱数。
02 导出箱唛按 cartonCode 生成 QR / Code128 标签。批量打印 PDF，可选纸张/标签规格。
03 手机/扫码枪扫描通过 POST /scan-events/ 幂等记录 cartonCode、operator、时间。绿：正确；橙：重复；红：未知箱号/不属于该 Shipment。
04 核对差异按 carton manifest 比较实际扫描和待出货箱。剩余未扫数量、重复扫描、SKU/箱数异常实时显示。
05 确认出货具备权限的人员确认全部必扫项完成或记录例外理由。可导出韩文装箱扫描核对报告。

数据保护与权限

  • 箱唛编码只包含不可预测 opaque cartonId/短校验码或经签名的短期 token；不要在 QR 明文中放客户手机、地址、发票单价或内部 API 密钥。
  • 扫码枪当作键盘输入应支持；手机摄像头依赖 HTTPS 和明确授权，提供手动录入退路。
  • 每个 ScanEvent 记录 teamId, shipmentId, cartonId, eventId, actorId, scannedAt；Event ID 唯一、重复请求不重复计数。
  • 仓库人员需最小权限角色；浏览器只读显示扫码结果也要检查 Team 隔离。
  • 扫码完成是“业务核对已完成”，不是法定通关、真实运单承运或出厂品检认证。

CHAPTER 15 · SECURITY

数据安全、租户隔离和业务校验门槛

当前已经有 Team 与 Session/CSRF 的基础，不意味着可以跳过生产安全验收。

风险必要控制验收用例
跨 Team 越权所有 Shipment/Revision/Plan/Scan/Document/Asset 的列表、详情、状态、下载都以 membership 限制。A Team 的成员知道 B Team UUID 仍返回不泄露敏感信息的 404/403。
权限角色owner/admin/editor/viewer 按操作最小化；确认/扫描、邀请、删除区分权限。viewer POST confirm 或导入 commit 被拒绝。
文件攻击格式白名单、真正 Zip/XLSX 结构校验、Zip bomb 限额、文件扫描、解析执行隔离、CSV 公式注入保护。伪装 XLSX、异常 ZIP、恶意表格和超大文件不会拖垮 API。
引擎资源耗尽Node HTTP 入口限制 body bytes、计算上限、超时、并发、内存，放在独立 internal network。极端 payload、400+ 单位超限、连续高并发仍可获得稳定错误。
会话与登录CSRF、Secure/HttpOnly Cookie、SameSite、密码恢复、邮箱验证、登录节流、可选强制登出。没有 CSRF 的更改请求失败；连续错误登录限速。
内容与金额Money Decimal、ISO currency、业务枚举强校验、反序列化限制、公式注入转义。多币种不会无汇率强行比较或求总额。
报告下载报告与 FileAsset 均团队鉴权；短期访问；原始 Excel 不放公开路径；下载和移除都有审计。过期下载 410；越权下载 404；导出不泄密。
隐私生命周期可查看数据用途、数据删除/导出、文件过期实际清理、备份生命周期可说明。文件过期不只设 expiresAt 字段，还应被后台任务真正清理。
可观测性requestId / jobId / shipmentId 串联日志；密钥、Cookie、客户整表及个人信息不入日志。提交失败能追踪问题但日志不含原始敏感文档。

CHAPTER 22 · DECISIONS

未确认项与推荐默认值

这些是业务决策，不是源码能推出来的事实。为便于 AI 继续开发，给出保守默认；真实客户数据到来后再调整。

待确认保守开发默认影响
Cargo.qty 究竟指 PCS 还是 CTN？旧 scheme 标 unknown；正式出货需用户确认P0 数据迁移。
净重如何获取？正式单据只接受用户提供/确认；未知为空并明确错误PL 准确性。
一个纸箱是否可以混多个 SKU？V1.4 初版单 SKU/箱；数据模型预留多 SKUCartonization 难度。
是否允许产品倒置？默认仅水平旋转，用户明确勾选额外方向算法约束。
纸箱标准库来源？先允许客户自定义与用户维护的箱规，不冒充全韩统一标准箱规推荐可信度。
发票金额口径？按 explicit currency 和 decimal 精度；税/保险/折扣单列，不默认为含税CI 合计与运费。
“确认出货”是谁可以操作？owner/admin/editor 可确认；viewer 只读，后续配置细粒度角色扫码/工作流权限。
韩国正式托管区域？先评估韩国区域与跨境数据流，未确认前不承诺某地区已合规云服务/隐私。
